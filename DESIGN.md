# Design: packaging scripts

## Pattern map

| Where | Pattern | Why |
|-------|---------|-----|
| `actions/package-*/package.sh` | Template method | build once, then one function per requested format |
| `actions/plan/plan.py` | Facade | caller inputs in, one validated JSON plan out |
| `scripts/lib.sh` `package_groups` | Value object | a group (cargo package + its binaries) is a plain `pkg<TAB>bin,bin` line, no behaviour |
| `scripts/linux-pkg.sh` `deb_package`, `rpm_package` | Strategy | one function per native format, each builds ONE cargo package; the Template method calls it per group |
| `actions/smoke/smoke.sh` | Strategy | one function per format (deb, zip, msi, exe): install like a person, start every binary, remove again |
| `scripts/bump-components.sh` | Template method | per program repo the same steps: fresh worktree, set the tag (`set_components_tag.py`), `cargo update`, gates, push the branch (does not convert programs) |
| `scripts/check_rust_rules.py` `check_blinc` | none | rule, per repo on via `.fs-rules.toml` `blinc = "components-only"`: no `blinc*` dependency, `[patch]`/`[replace]`, one fs-components tag |
| `scripts/check_blinc_lock.py`, `scripts/blinc-approved.txt`, `scripts/approve-blinc.sh` | none | lock rule, ALWAYS on (called by `check_rust_rules.py`): Blinc packages in `Cargo.lock` only from the approved fs-blinc tag + full sha; `approve-blinc.sh <tag>` writes the approved tag (maintainers) |
| `scripts/typing-test.sh` + `scripts/typing-test/` | Facade | one command (binary in, exit code and junit/json out) over a virtual KWin, the key injector (`inject/`, a small Wayland client: Adapter to KWin's `org_kde_kwin_fake_input`), the pictures (`session.sh`) and the checks (`analyze.py`, `fieldcheck.py`) |
| `scripts/typing-test/session.sh` | Template method | wait for the window, find the field by its caret, type one character, picture, clear; then two text parts; then the timed run. Apps may replace `focus()` with a scenario file |
| `scripts/virtual-session.sh` | Guard | the ONE protection for virtual sessions: `vs_guard` refuses (exit 97) unless runtime dir, D-Bus, Wayland/X point at a private session; wrappers `vs_run`/`vs_dbus`/`vs_qdbus`/`vs_gdbus` guard before every call; sourced by typing-test.sh and session.sh |
| `actions/typing-test` | Facade | the same script as a composite action for the app repos (see below) |
| `tests/packaging/`, `tests/typing-test/` | none | test support |

## Signing leaves nothing behind (`actions/sign-files/sign.sh`)

The key ring (`GNUPGHOME`, mode 0700) and the passphrase file (0600) are created with `mktemp` under `RUNNER_TEMP`, and an `EXIT` trap removes them at the end of every call, also after an error: `gpgconf --kill gpg-agent`, `shred -u` (else `rm -f`) of the passphrase file, `rm -rf` of the one GNUPGHOME directory. Only these two own paths are touched, no globs. The action calls the script once per mode (`packages`, `detached`), each call imports the key again, so later steps of the job find neither key nor passphrase. Test: `tests/packaging/sign.sh` (generates a throw-away key; RUNNER_TEMP is empty after a good run, after a bad mode and after a broken key). Known limit: the secret and the passphrase stay in the signing step's own environment (`GPG_PRIVATE_KEY`, `GPG_PASSPHRASE`) while it runs.

## Internal action references (2026-11-11)

Composite actions in `actions/` never call another fs-release action by `uses: FreeSynergy/fs-release/...@ref` (a pinned action would pull later `main` states of the other one). `sbom` and `licence-check` run the shared `actions/install-tools/install.sh` by path (`$GITHUB_ACTION_PATH/../install-tools/install.sh`), so they always use the script of their own commit. `lint.yml` fails on any such `uses:` in `actions/`. Known limit: the reusable workflows (`release.yml`, `check.yml`, `_release-*.yml`) still call actions and each other with `@main`: `./` in a reusable workflow means the CALLER's repository, and a commit cannot name its own SHA, so `scripts/pin-refs.sh <tag>` rewrites them on the release commit.

## Blinc lock rule (always on)

`scripts/check_blinc_lock.py` runs inside `check_rust_rules.py`, so inside the `check` gate of every repo, without a switch: every package in `Cargo.lock` whose name starts with `blinc` or whose source names blinc (forks like `blinc-app-fix`, `blinc-layout-fix`, crates.io, path) must have the source `git+https://github.com/FreeSynergy/Blinc?tag=<tag>#<sha>` with `<tag> <full sha>` from `scripts/blinc-approved.txt`, the ONLY source of truth (a moved tag has another sha and is red). Two Blinc sources in one lock are red; no Blinc packages (or no lock) is green. With Blinc in the lock, `.cargo/config(.toml)` may not set `paths` or `[source.*] replace-with` (a vendored fork would leave the lock unchanged). The error lists one line per package, then once the count and the fix: programs take Blinc only through fs-components; `scripts/approve-blinc.sh <fs-blinc-N>` is for maintainers approving a new tag. Approving a new tag turns every program red at once (they still hold the old tag): prepare the programs first with `bump-components.sh` (branches ready), then approve and merge. Several tags may be approved at once for a transition: `scripts/blinc-approved.txt` has one `<tag> <full sha>` per line, optionally `# expires YYYY-MM-DD` in the same line (a whole-line comment is ignored). A lock is green when ALL its Blinc packages have the SAME source and that source is an approved entry; a lock that mixes two tags (3 and 3.1) stays red even though both are approved. From the day after its expiry date an entry is an error for EVERY repo (red gate, also without Blinc) and approves nothing: the transition cannot stay forever. `scripts/approve-blinc.sh` has `list`, `add <tag> [--expires YYYY-MM-DD]` (sha by `git ls-remote`, annotated tags peeled with `^{}`, atomic write), `remove <tag>` and `replace <tag>` (also the old form `approve-blinc.sh <tag>`: exactly this tag afterwards). Transition: 1. the new tag (fs-blinc-3.1) is set in the Blinc fork; 2. `approve-blinc.sh add fs-blinc-3.1` (an expiry on the old one, `add fs-blinc-3 --expires ...`, is optional); 3. fs-components moves to 3.1 and gets its tag; 4. the programs follow with `bump-components.sh` (each lock holds only one of the tags at any time, so each stays green); 5. `approve-blinc.sh remove fs-blinc-3`. Tests: `tests/packaging/blinc_lock.sh`. Known limit: only the ROOT `Cargo.lock` is read; nested locks (for example `scripts/typing-test/inject/` here, or a vendored workspace in another repo) are not checked. Likewise the `.cargo/config` check sees only files inside the repo: a `config.toml` in `CARGO_HOME` (`~/.cargo`) or in a directory above the repo is not read, so a developer's own machine can build against a replaced Blinc unseen; the lock on the pushed branch and the CI runner (no such file) are what decide.

## Typing test (`actions/typing-test`, `scripts/typing-test.sh`)

Interface of the action (inputs): `app-binary` (required), `app-args`, `click-in-window` (x,y from the window's top left corner; preferred) or `click` (on the 1280x800 screen) or `scenario` (bash fragment defining `focus()` for apps that need clicks to reach the field), `field`, `text-width`, `ref-font`, `layout` (default `de`), `max-ms` (default 8), `enforce-ms`, `size`, `settle`, `inject`, `name`, `install`. Outputs: artefact `typing-test-<name>` with `junit.xml`, `result.json`, `shots/` and logs; the step fails if a check fails (exit 1) or the test could not run (exit 2).

What is checked: each of `a Ä ä ö ü ß @ € { } [ ] \ | ~ µ` (Shift and AltGr) arrives in the focused field and is drawn as that glyph (compared with a reference rendering of all printable ASCII and the German extras in DejaVu Sans, the typed one must be among the best three; `|` is only told apart from bars), the text is visible and the caret stands right behind it, and the median key-to-picture time (client Wayland trace) is within `max-ms`. A wrong layout turns it red. Without a GPU (GitHub runner) the time is reported, not enforced.

Field and caret (2026-11-11): the field is the rectangle around the click point (`fieldcheck.py field`: top and bottom are long unbroken lines across the click's column, left and right are edges over the middle 60 % of that height, so rounded corners work); ring and border are cut off (4 px). The caret is searched INSIDE that rectangle only (so a blue button beside or above the field, or a focus ring in the same pixel column as a button, cannot be taken for it): a narrow bar (at most 3 px, 10 px to field height) that differs between any two of up to 7 pictures taken more than 300 ms apart (it blinks; the union decides), else a narrow saturated-blue bar in any picture, else (third stage) a light-blue bar of 2-3 columns and at least 12 px height (`FAINT_MINH`; thresholds `b-r>40` and `b>235`, inside the field only): the caret frozen at a faint point of its fade while the app idles, measured colour (192,216,247) in a laptop run, range (111,167,236) to (201,222,248) over 162 real pictures, where the only light-blue bars were the caret itself (2 columns, 15 px); the app draws no light-blue fringes at glyph edges, and a 1-column edge or a short piece is therefore refused (tests `fringe without caret`). Among several candidates the one nearest to the end of the text counts. Known limit: a light-blue selection of 2-3 columns would pass (see `docs/known-limits.md`). An explicit `field` is taken as given, the caret must lie inside it. The caret must sit 0..4 px behind the last glyph; a caret far before it stays red. Known limit: HiDPI 2x with a 2 px wide caret scaled to 4 px stays red (bar at most 3 px; the tests run at scale 1). Tests with synthetic pictures (button right/above, ring, blink phases, negative): `tests/typing-test/caret.sh`. Cause of the red runs in fs-store and fs-files: with identical pictures the old fallback took the first blue bar of the whole screenshot (the Add/Save button).

Glyph check (2026-11-11): the reference size is fitted over all glyphs that arrived (best sum of similarities), no longer taken from the height of 'a', so one glyph that did not arrive (the field still shows the old content) cannot spoil the other 15. The glyph's shape is cut at a lower ink threshold (40) and without the pale edge of the caret; the field's inside leaves 6 px left/right and 4 px top/bottom (rounded corners). `tests/typing-test/glyphs.sh` runs `analyze.py` on synthetic result directories: all right, first character not drawn (only that one red), wrong layout (red). Repeats (`runs`, default 3; locally before a tag 10): the action calls `scripts/typing-test-runs.sh`, which runs the test N times, each with a fresh KWin and a fresh app window (`TT_OUT/run-i`), and is green ONLY if ALL runs are green. Reason: rare faults (a field that stays dead in about one run of eight, found 2026-11-11) are to be found, not rolled away; a run that is red once is red. Output: per run its number, green/red/did not run and the red checks (`summary.txt`, `summary.json`, the job summary: "x of N runs red"); the artefact holds the pictures and `result.json` of every run. Exit: 1 if any run is red, else 2 if one did not run. Cost: about 1-2 minutes per run on the runner. Test: `tests/typing-test/runs.sh` (fake single run: one red among three is red, all green is green, could-not-run is 2).

Near twins (Opus review): beside "among the best three", the typed character must rank above its twin: `Ä` over `A`, `ä` over `a`, `ö` over `o`, `ü` over `u` (decided by the glyph's height, since the marks blur at small sizes), `[` `{` over `(`, `]` `}` over `)` (decided by the score); `tests/typing-test/glyphs.sh` has each pair. Reference font: the apps draw with `sans-serif`, which is DejaVu Sans on the Ubuntu runner and on the laptop, so that is the default; with another font (Noto) `a`/`ä`, `ü`/`u` can no longer be told apart reliably. Give the font the app draws with in `ref-font` (env `TT_REF_FONT`); set it to Inter in the app repos when Inter ships with the apps. Finding the test made visible: in fs-files (and fs-store before the fix of its first key) the FIRST key typed after the click is inserted but not drawn until the next key arrives; a check "char 'a' arrives" turning red there is correct.

Virtual sessions, never the real one (2026-11-11, after a spike ran a KWin script against the real user bus): every test, spike and the typing test sources `scripts/virtual-session.sh`. How to start one: call `vs_capture_real` first (remembers the real session's values), start the session with its own `XDG_RUNTIME_DIR` under `/tmp` or `/srv/FreeSynergy/.scratch`, `dbus-run-session` for the private bus, no `DISPLAY`, own Wayland socket (`scripts/typing-test.sh` does all of this), and call `vs_guard` inside. Anything that talks to D-Bus, KWin, input or config (`qdbus`, `dbus-send`, `gdbus`, `kwriteconfig`, `xdotool`, `wtype`, KWin scripts) goes through `vs_run <tool>` or `vs_dbus`/`vs_qdbus`/`vs_gdbus`, never bare. The guard refuses (exit 97, message) on: the real bus (`/run/user/<uid>/bus` or the address seen before the start), an empty bus (no fallback to the default), a runtime dir under `/run/user` or outside `/tmp`/`$TMPDIR`/scratch, the real `WAYLAND_DISPLAY`, any `WAYLAND_SOCKET`, `DISPLAY`, and an empty environment (nothing is guessed). Test: `tests/typing-test/vsession.sh`. Hardened (Opus review): symlinks are resolved (`readlink -f`) for the runtime dir and the bus socket; `%` (D-Bus decodes `%2e%2e`) and `;` (several addresses) and any address that is not a plain `unix:path=...[,guid=...]` are refused; abstract addresses are refused (no file path, nothing says they are private; the session bus therefore must be a path socket, as `dbus-run-session` here gives); `vs_run` on `dbus-send`/`gdbus`/`busctl`/`qdbus*` refuses `--address`, `--system`, `--bus`, `-a`, `-H`, `-M` and `unix:`/`/run/user` arguments (`--session` is fine: it uses the guarded environment). `VS_ALLOW_X=1` only for a kwin started with `--xwayland` (its own private `DISPLAY`, never the real one). Supported runner: ubuntu-24.04 (dbus 1.14.10 gives `unix:path=/tmp/dbus-...`); ubuntu-22.04 gives `unix:abstract=` and is NOT supported (the guard refuses); the way out would be an own dbus config with `<listen>unix:dir=$XDG_RUNTIME_DIR</listen>` and no include of `session.conf`. Known limits of the wrapper: `vs_run env gdbus --address=...` and `vs_run sh -c '...'` are not caught (convention only: call the tool directly). Known limit: it checks the environment of the calling process and the bus arguments, not what a tool does with another absolute path it was given.

Isolation: own runtime directory and private D-Bus, own Wayland socket, no `DISPLAY`, toolkits forced to Wayland, own process group killed at the end; `tests/typing-test/isolation.sh` proves it. Known limits: picture-based (no accessibility read-out); window placement is by KWin 5.27 (Ubuntu) or 6.x (laptop), so clicks are relative to the window; pictures cost about one second each, a run takes minutes. The probe workflow `typing-test-probe` runs on push to the branch only; after the merge it is `workflow_dispatch` only.

## Rules

- A binary of a workspace package under `crates/` that is not in `binaries` fails the plan (it would otherwise never be packaged). Opt out per binary or with `*` via the `ignore-binaries` input; there is no implicit default packaging.
- A binary belongs to the cargo package that provides it (the plan's `cargo-package` wins when it provides it too).
- One deb, rpm and msi per package (a single-package repo keeps `<name>-<version>-windows-<arch>.msi`, several get `<package>-<version>-windows-<arch>.msi`; an existing `wix/main.wxs` of a package is kept); tar.gz, AppImage, Arch, zip, macOS stay one artefact with all binaries.
- Single-package repos behave as before; `tests/golden/capnpc-*` pin plan JSON, commands and file names.
- cargo-generate-rpm `-p` is a package *directory* relative to the workspace root, cargo-deb `-p` is a package *name*.

## File names

- Every released file name (`dist/`, `SHA256SUMS.txt`) uses only `[A-Za-z0-9._-]`. GitHub rewrites other characters on upload (rpm `~` became `.`), which made `SHA256SUMS.txt` list names that did not exist.
- Rule: each other character becomes `-` (rpm/deb `0.6.1~rc.2` -> file `...-0.6.1-rc.2-1.x86_64.rpm`). The version *inside* the package stays `0.6.1~rc.2` (needed for correct rpm/deb ordering); only the file name changes.
- Implemented by `dist_normalise` / `dist_check` in `scripts/lib.sh`: `package-linux` normalises, the `checksums` action normalises again (SBOM etc.), checks, then hashes. Two files that would collide fail the run.

## Features

- The plan's `features` go to every `cargo build` (one per package) and to `cargo deb`, filtered to the features each package declares (`pkg_features`), because cargo rejects `-p PKG --features X` when PKG lacks X. `dep/feature` entries pass through.
- A feature declared by no built package fails before the first build. `cargo generate-rpm`, `cargo wix --no-build`, tar/zip/dmg/AppImage/Arch reuse the already built binaries and need no features.

## State

- Done: per-package build, deb, rpm; tests with stubs and a real `cargo generate-rpm` build.
- Unsupported / not done: `cargo-deb` is not installed locally, so the real deb build is tested only in CI-like environments that have it.
- Smoke test (Thread D, 2026-11-10): `actions/smoke`, called from `_release-linux.yml` (job `smoke-deb`: `debian:13` and `ubuntu:24.04`, both architectures, `docker run` with the artefacts mounted) and `_release-windows.yml` (job `smoke`: zip, msi via `msiexec /qn`, `-setup.exe /S`, uninstall checked). Every binary is started with `smoke-args` (default `--version`) and must exit 0; a failure stops `finalize`, so no draft is created. Switch off with `smoke: false`. Tested here: the deb step in real `debian:13` and `ubuntu:24.04` containers (podman) with a hand-made deb, and the call/failure paths with stubs. Run on real GitHub runners from a throwaway branch (Debian 13 and Ubuntu 24.04 on x86_64 and aarch64, Windows x86_64 zip, msi and setup.exe with uninstall; fixture `tests/fixtures/hello`, kind `app`). **Not yet run:** kind `daemon` (msi now default there), several packages in one repo, Windows arm64 (zip only), the real `finalize` gating.
- AppImage, Flatpak, Arch: unchanged. AppImage/Arch/zip/dmg bundle all binaries into one artefact on purpose; Flatpak builds from the app repo's manifest.

* **One measure (2026-11-08, Strategy; one definition 2026-11-10).** `scripts/gates.sh <root>` is the ONLY definition of the four checks: `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings -W clippy::pedantic`, `cargo test --workspace --all-features`, `check_rust_rules.py`. `check.yml` does not repeat them; it calls `actions/gates`, which runs `gates.sh` from the same ref. `tests/packaging/gates.sh` fails if check.yml grows its own cargo commands. The local threads use this file (the copy in `.wt-doc-strategy/scripts` is older and not authoritative).
* **Pinned toolchain (2026-11-10).** `RUST_VERSION` (exact `x.y.z`) is the one Rust version for the gates AND the release builds: every `actions/setup-rust` call in this repo (check.yml, ci.yml, `_release-linux/macos/windows.yml`) uses `toolchain: pinned` (also the action's default); `gates.sh` exports it as `RUSTUP_TOOLCHAIN`. Programs take it over without a file of their own. Reason: with unpinned stable, every new clippy lint turned all repos red at once (~228 red runs); and we must ship the compiler we tested with. Exceptions, by design: (1) the `msrv` job in ci.yml builds with the program's declared MSRV (that is its purpose); (2) Flatpak builds with the SDK/manifest of the app repo; (3) Arch and the OCI image only repackage already built binaries (no compile); (4) mobile is a placeholder. All release targets (x86_64/aarch64 linux-gnu, x86_64/aarch64 windows-msvc, x86_64/aarch64 apple-darwin) exist for the pinned version (checked in the channel manifest when `RUST_VERSION` changes). Windows and macOS are built natively on their runners, no cross-compiler. `tests/packaging/gates.sh` fails if any workflow or action names `stable` or a `toolchain:` other than `pinned` (except the msrv input). Update path: ONE deliberate bump PR in fs-release that changes only `RUST_VERSION`, so gates and release move together; before merging, run `scripts/gates.sh` on every program repo (fresh clones of main) with the new version and check the release targets exist; repos that turn red are fixed first, then the bump merges. Because programs use `check.yml@main`, merging the bump takes effect everywhere at once, so it never merges red.

## Release to catalog (Q2b, 2026-11-10)

Flow: (0) Opus review of the change BEFORE the tag, never inside a workflow -> (1) tag `vX.Y.Z` pushed by hand -> (2) `release.yml`:
plan, build, smoke test, SBOM, signatures, SHA256SUMS, attestation, draft -> (3) job `publish` (`_release-publish.yml`, `actions/publish-release`):
draft -> Pre-release, only when SHA256SUMS.txt, every file and every `.asc` are attached; idempotent; own `GITHUB_TOKEN`
(`contents: write`) -> (4) fs-catalog's `bump` workflow (every 15 minutes) finds the new published Pre-release, raises the tag in
`packages.toml` and starts `sign`. **No secret and nothing cross-repo:** direction is pull (fs-catalog reads public releases), so no
token for fs-catalog is passed to the program repos. Delay between publish and catalog: up to 15 minutes (plus the sign run).
Drafts and releases with missing files are skipped with a warning, never a red run.

Recommendation: switch on "Immutable releases" (repo Settings, General) in every program repo, so a published release and its
assets can never be changed or replaced, not even by an owner. Not switched on by this workflow; the repo owner does it.

## Blinc in one place

- `scripts/bump-components.sh [--dry-run] <tag> [repo ...]` lives here and not in fs-components: it is release machinery over many repos (it uses `gates.sh`, the same measure as CI); fs-components is a library and must not know its dependants. First it checks that the tag exists in the fs-components repo (`git ls-remote --tags`). Per repo it creates a FRESH worktree `.wt-bump-<repo>` from `origin/main` (an existing one is an error, never reused: it may hold old state), lets `scripts/set_components_tag.py` set `tag = "<tag>"` on EVERY dependency whose `git` is the fs-components repo (any name, `package =`, inline or table form, workspace/dev/build/target tables, Cargo.toml at any depth outside `target/` and `.wt-*`; rev/branch removed) and verifies the result with a TOML parser (a form it cannot edit fails, nothing is written), runs `cargo update -p <url#name@version>` for every package of that git source (the spec rules out a same-named package from another source), `gates.sh`, and pushes `HEAD:refs/heads/bump-components-<tag>` only when green. Already on the tag = ok and nothing pushed; no fs-components dependency found = failure. Never a tag, never a merge; `--dry-run` stops before the push. Each repo runs in its own shell, so one red repo does not stop the others (exit 1 at the end).
- The script does NOT convert programs: it removes no `blinc*` line and no `[patch]` and rewrites no `use`. The first move of a repo to "Blinc only through fs-components" is manual work per repo; it ends by adding the switch below. Only then does the script keep the repo current.
- Rule in `check_rust_rules.py` (`check_blinc`, the `Cargo.toml` part), switched per repo: the programs call `fs-release/.github/workflows/check.yml@main`, so a rule that is always on turns every program's CI red at once (they still carry `blinc_*` and `[patch]`). That is wanted for the lock rule below; this Cargo.toml rule stays per repo. The rule runs only when the repo root has `.fs-rules.toml` with `blinc = "components-only"` (default `off`; any other value is an error). Migrating a repo by hand includes adding that file. When on, a repo fails on: a `blinc*` dependency (also renamed through `package =`, by git url, in `target.*`, dev and build tables), a `[patch]` or `[replace]` entry naming blinc in any Cargo.toml or `.cargo/config.toml`, and two different fs-components tags/revs in one program (two Blinc). Exempt only the real fs-components repo: `crates/fs-components/Cargo.toml` must be a package named `fs-components` (and name that repository if it names one); an empty file there is no exemption. Cargo.toml in `target/`, `.git/` and nested `.wt-*` worktrees are not looked at. Cargo applies `[patch]` only at the top of a build, so such a line in a program is either redundant or a second, diverging pin.
- Tests: `tests/packaging/rules.sh`, `tests/packaging/bump.sh` (a fake origin and a file:// fs-components repo with tags, stub gates, one run with the real `cargo update -p`).

## Release chain (`crates/fs-release-chain`, stage 0 of the workflow standard)

One command runs the release chain: `fs-release-chain run --version 0.0.9 --repo-dir <worktree> --catalog <fs-catalog checkout> --reach public`. It is a developer tool (ADR 0063: one Rust program, no shell as a switch); it calls `git`, `gh` and the existing `scripts/` (`gates.sh`, `check_blinc_lock.py`), it replaces none of them. The programs are not changed.

**Output** is one line (plus `log: <path>`): `DONE ...` (exit 0), `HALT <step> <reason> needs: <what>` (exit 10, somebody else has to act: approval, reach, queue stall) or `RED <step> <first error line>` (exit 1, a check is red). Both stop the chain at once; nothing after the step runs. Run the same command again to go on.

| Command | Risk | Reach | What it does (and when it is already done) |
|---|---|---|---|
| `gates` | start | local | Blinc lock check (`check_blinc_lock.py`, skipped without `Cargo.lock`), then `scripts/gates.sh` (optionally behind `--wrap`, e.g. `build-slot.sh`). Done: gates were green for this commit before |
| `review` | view | local | `.opus-ok` must say JA for this repo and exactly this head sha, else HALT |
| `push` | publish | shared | `git push origin HEAD:refs/heads/<branch>`, never forced. Done: remote head equals local |
| `wait-ci` | view | shared | polls the runs of the pushed commit; green, red, or HALT. One retry of a red run only when its log shows a runner/network problem (DNS, apt) |
| `merge-ff` | publish | public | needs a green `wait-ci` for this sha; pushes `sha:main` only when main is an ancestor (else RED "rebase needed"). Done: main is at sha |
| `tag` | publish | public | annotated `v<version>` on main = sha, pushed. Done: tag on that commit; tag on another commit is RED, never moved |
| `release` | publish | public | waits for the `release` run on the tag (one retry of a red run), then `gh release edit --draft=false --prerelease`. Done: release not a draft |
| `bump` | publish | public | sets `tag` of the package with this `repo` in the catalog's `packages.toml`, commits, pushes. Needs a published release. Done: tag already there |
| `sign` | publish | public | waits for the catalog `sign` run on the bump commit (starts it once by hand when the bump changed nothing). Done: signed for this commit before |
| `check` | view | local | fresh clone of the catalog, `gpg --verify` against `release-signing-key.asc` in a temporary home, and the version is in `catalog.xml` |
| `report` | view | local | at most ten lines to `<git-dir>/fs-release-chain/report-<version>.txt` |

`fs-release-chain step <name> ...` runs one command, `list` prints the table, `verify` checks the chain file. The run log `chain-<version>.jsonl` (same directory) holds every result with the commit it ran for; it only speeds things up and carries facts between steps (catalog commit, "retried once"). Nothing is trusted from it for safety: every command looks at the real state first.

**Approval (`.opus-ok`, not committed, git-ignored):**
```yaml
repo: FreeSynergy/fs-store
sha: <full 40-hex head>
date: 2026-11-12
verdict: JA        # NEIN stops with review-no
by: opus
```
Checked by `review` and again before every command of risk `publish` (a new commit during a run halts the next publish step). A new commit on the branch makes it worth nothing. The tool cannot tell who wrote the file: that the approval comes from Opus is a rule of the process, not something this file proves.

**Reach limit.** Each command carries risk (view < open < start < install < system < publish) and reach (local, shared, public). A run may only touch up to `--reach` (default `local`); a step above it is `HALT <step> reach-limit`. So a chain started during a push pause stops before `push`.

**GitHub rate limit.** One `gh run list` per 30 s at most (enforced in one place, shared by all waits; `--poll-secs` can only raise it), growing by half up to 120 s. A wait ends with HALT when no run shows up for 10 min (`ci-missing`), when all runs only queue for 20 min (`ci-queue`), or after 90 min in total (`ci-timeout`). Other calls (`release view`, `ls-remote`) are single.

**FS profile precursor.** `chains/release.chain.yaml` lists exactly the commands above; `verify` and a test refuse any difference in name, order, risk or reach. It is not run by a generic runner (no `swf-core`); the program runs the list. Mapping to Serverless Workflow, for the later runner: `chain`/`version` -> `document.name`/`version`; `catalog: fs/0.1.0` -> the function catalog; each `steps[]` entry -> one task in `do` with `call: fs.<command>`; `risk`, `reach`, `actor` -> task `metadata`; HALT/RED -> an error type (`authorization`/`validation`/`runtime`) ending the run, resume = run again.

**Patterns.** Strategy (`Step` trait, one type per command; `Runner` and `Clock` behind traits so tests use a fake clock), Registry (`registry.rs`: names and order), Template method (`runner.rs`: reach, approval, run, log around every command), Adapter (`gh.rs`), Facade (`git.rs`, `cli.rs`), Specification (`approval.rs`), State (`poll.rs`), Repository (`ledger.rs`). Output lines are developer text, English, not translated.

**Tests** (`crates/fs-release-chain/tests/`): real `git` against local bare repositories as remotes, a fake `gh` and `gpg` (shell scripts first in `PATH`, answers from files, every call logged), a virtual clock. Covered: green chain to DONE (main, tag, catalog commit, release, report), red CI, red gates with log, Blinc lock red (real `check_blinc_lock.py`), new commit after approval, approval missing / NEIN, a commit in the middle of a run, reach limit, partial run then repeat, full repeat changing nothing, queue stall (HALT, at most one query per 30 s), run that never appears, one retry for a DNS failure and none for a code failure, tag on another commit, bad catalog signature.

**Limits (honest).**
- Nothing has been run against real GitHub: during the push pause no call went out, so the `gh` flags and JSON fields (`run list --json databaseId,workflowName,status,conclusion,headSha,headBranch`, `release view --json isDraft,isPrerelease`, `release edit --draft=false --prerelease`, `workflow run`) are from `gh` documentation, and the fake accepts what the code sends. The first real run must be watched, with `--reach shared` first.
- `merge-ff` pushes to `main` directly. If branch protection demands a pull request, this step is RED and the chain needs a PR step.
- CI is "all runs of the head commit on the branch"; there is no list of required jobs yet. A run of a workflow that is red but not required would stop the chain.
- Not included: `typing-test` (only UI repos), the user-test halt (the DONE line says `next: user-test`), `fs-store check` (the signature and the entry are checked directly instead, so no installed state is touched), writing the approval file (a person or the coordinator does).
- The GitHub token needs write access to the program repo (branch, tag, release) and to `fs-catalog` (push to main); the catalog push is a normal push, the bot commit "refresh and sign" is made by `sign.yml`.
- `scripts/check_blinc_lock.py` crashes with a traceback when the repo has no `Cargo.lock` (its doc says "nothing to check"); the chain skips the call in that case. The script itself was not changed.
- Two chains on the same release at once are not protected against (no lock file).
